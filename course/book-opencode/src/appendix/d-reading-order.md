# 부록 D: 추천 독서 경로

본문 서문에도 경로를 적었지만, 이 부록은 각 경로가 왜 그런 순서를 갖는지 조금 더 실무적으로 설명한다.

## 1. 하니스 설계자용 경로

대상 독자:
에이전트 런타임이나 코딩 에이전트 프레임워크를 직접 만드는 사람

권장 순서:

1. `2장` 부트스트랩
2. `3장` 에이전트
3. `4장` 도구 계약
4. `5장` 메시지/세션 모델
5. `6장` 프롬프트 조립
6. `7장` provider 정규화
7. `8장` compaction
8. `19장` 권한
9. `25장` 파일 수정 의미론
10. `29장`과 `30장` 종합

이유:
이 경로는 "에이전트 하니스의 뼈대"만 모아서 본다. UI, 문서, 제품 표면은 뒤로 미룬다.

## 2. 제품 엔지니어용 경로

대상 독자:
TUI, 앱, 데스크톱, SDK를 함께 운영하는 제품 엔지니어

권장 순서:

1. `1장` 토폴로지
2. `10장` TUI
3. `11장` 로컬 제어면
4. `12장` 웹/앱/데스크톱
5. `13장` SDK
6. `21장` 지속성
7. `22장` 이벤트/운영 가시성
8. `23장` 공유/동기화

이유:
같은 코어가 여러 표면으로 어떻게 퍼지는지 먼저 잡아야 제품 비용 구조가 보인다.

## 3. 확장 생태계 설계자용 경로

대상 독자:
플러그인, 스킬, MCP, 외부 자동화 채널을 설계하는 사람

권장 순서:

1. `4장` 도구 표면
2. `14장` 서버 플러그인
3. `15장` TUI 플러그인
4. `16장` 스킬
5. `17장` MCP
6. `18장` 워크스페이스
7. `13장` SDK

이유:
OpenCode는 확장을 하나의 메커니즘으로 통일하지 않는다. 그래서 확장 채널별 경계를 비교해서 읽는 편이 낫다.

## 4. 안정성/운영성 중심 경로

대상 독자:
권한, 추적, 복구, 상태 일관성이 중요한 시스템을 운영하는 사람

권장 순서:

1. `5장` 세션 모델
2. `8장` compaction
3. `19장` 권한
4. `20장` 외부 디렉터리와 브레이크
5. `21장` 지속성/복구
6. `22장` 이벤트와 운영 가시성
7. `27장` snapshot

이유:
OpenCode의 품질은 기능 수보다 상태와 운영성을 어떻게 따로 모델링했는지에서 드러난다.

## 5. 시간이 없을 때 보는 최소 경로

정말 시간이 없다면 아래 여덟 장만 읽으면 된다.

1. `1장`
2. `3장`
3. `4장`
4. `5장`
5. `8장`
6. `11장`
7. `19장`
8. `29장`

이유:
토폴로지, agent, tool, session, compaction, control plane, permission, builder lesson만 봐도 OpenCode의 설계 습관은 충분히 보인다.
